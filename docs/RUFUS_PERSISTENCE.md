## Why the DD choice was absent

Upstream Rufus source at commit `acf7de640848ab249bedeb6feb59b33001f656b6` distinguishes these write paths:

- [`src/rufus.c`](https://github.com/pbatard/rufus/blob/acf7de640848ab249bedeb6feb59b33001f656b6/src/rufus.c): the ISOHybrid ISO/DD prompt is guarded by `persistence_size == 0`. Nonzero persistence bypasses that prompt; its absence is not evidence that the user missed a button.
- [`src/format.c`](https://github.com/pbatard/rufus/blob/acf7de640848ab249bedeb6feb59b33001f656b6/src/format.c): the extracted-image path can add a persistence partition, labeled `persistence` for Debian-derived media.
- [`src/format_ext.c`](https://github.com/pbatard/rufus/blob/acf7de640848ab249bedeb6feb59b33001f656b6/src/format_ext.c): the persistence configuration it creates contains exactly `/ union\n`, meaning full-root union persistence, rather than this project's separately provisioned `/home union\n` test.
- [`src/iso.c`](https://github.com/pbatard/rufus/blob/acf7de640848ab249bedeb6feb59b33001f656b6/src/iso.c): extraction adjusts Debian `boot=live` kernel lines to include `persistence`.

This is inspection of a pinned upstream revision, not execution of the user's unreported Rufus version or inspection of their USB partitions. Source snapshots and SHA-256 evidence are retained outside the checkout at `~/gravestone-test-evidence/rufus-persistence-source/`.

## Loader diagnosis: reproduced and corrected in fixtures

The exact released 0.4.0 EFI executable was exercised under Debian bookworm OVMF using disposable GPT/FAT32 and MBR/FAT32 USB disk images. Both contained a separately read-back `.disk/info` marker. Both reproduced `error: no such device: /.disk/info.` and timed out at GRUB. The parent independently repeated both failing boots.

The installed `live-build 1:20230502` helper `/usr/lib/live/build/efi-image` assigns `PARTITIONLIST` inside a subshell, losing it before `grub-mkimage`. The released executable consequently has no embedded partition modules for its early filesystem search. The same generator also prematurely expands the GRUB runtime variables `$grub_platform` and `$lockdown`.

A narrow, exact-upstream-SHA-gated patch retains the partition list in the current shell and preserves those runtime variables. An executable generated by the patched helper booted both otherwise equivalent FAT fixtures, sourced the configuration and exited QEMU cleanly. The parent independently repeated both successful boots and inspected real embedded module records for `part_gpt` and `part_msdos`.

Each guest used 384 MiB RAM, one CPU, no NIC and a 40-second deadline. No host filesystem was mounted and no physical storage was selected. Evidence, serial logs, original/patched helpers, executable hashes and `parent-independent-comparison.json` are retained at `~/gravestone-test-evidence/rufus-persistence-boot/resumed-20261031/`.

The builder now tests the patched helper before expensive AI preparation and tests the actual shipped loader/template after image construction. The source suite at this checkpoint ran **113 tests: 110 passed, three existing optional integration checks skipped**. Independent review and the full-image/persistence acceptance remain separate gates. **These fixture results do not constitute a corrected release ISO, kernel/backend boot, graphical boot, or verified Rufus persistence.**

## Keep the test claims separate

The earlier 0.4.0 image passed raw/DD USB-as-disk firmware/backend tests and a separate direct-kernel notebook persistence test. Neither by itself proved the Rufus extracted/persistent layout:

1. **Raw/DD image:** original hybrid ISO attached as USB mass storage; no extraction or Rufus-created persistent partition.
2. **Existing persistence test:** original ISO supplies the live system; a separate emulated removable USB filesystem contains `/home union`. It exercises exact notebook bytes through two clean reboot cycles but bypasses firmware via direct-kernel boot.
3. **Small extracted-FAT fixture:** an actual OVMF boot can establish early loader discovery on GPT/FAT or MBR/FAT, with `.disk/info` present. A marker reached in such a fixture does not prove Linux, the backend, graphics or persistence.
4. **Rufus-like extracted/persistent layout:** still requires full-image firmware/backend boot and two clean reboot checks with boot files and a root-union persistence partition on the same emulated USB. A constructed equivalent is not execution of Rufus itself.
5. **Physical acceptance:** finally requires the intended computer and USB, exact image checksum, actual writer/version/settings, clean shutdowns and exact saved-note continuity. VM results do not replace this.

Do not relax `live-media=removable` or `persistence-media=removable-usb` to make a fixture pass: ordinary internal disks must remain outside automatic live-medium/persistence selection. Secure Boot remains unsupported.
